# Этап 1: защита локального хранения (P0)

Дата: 21 октября 2026 года. Продолжение [аудита](project-audit.md) и [плана](development-roadmap.md).

## Что изменено

Сохранены Context-провайдеры, AsyncStorage, production origin, название и EAS project ID. Новых зависимостей нет. Код не публиковался.

Небольшой общий `SafeStore` отделяет успешное чтение пустого профиля от ошибки чтения, неверного JSON и неподдерживаемой версии. Провайдеры больше не сохраняют стартовые пустые значения эффектом после любой попытки загрузки. Изменения проходят через последовательную очередь и становятся видимыми после успешной основной записи.

### Книга рецептов

- `recipe-book-v1`, `recipes` и `recipe-meta-v1` читаются независимо. Ошибка legacy-ключа не скрывает исправную основную книгу.
- Основной снимок остаётся `{ recipes, recipeMeta }`, legacy-зеркала — массивом и картой метаданных. При отсутствии книги и исправных legacy-данных выполняется совместимая миграция.
- Повреждённые/непрочитанные зеркала не переписываются. Исправные зеркала обновляются после commit основной книги.
- Повреждённая основная книга не заменяется fallback автоматически. Пользователь может подтвердить восстановление из валидных legacy-данных. До замены исходные строки архивируются и прочитываются обратно для проверки. Отказ архивации блокирует замену.
- При отсутствии исправного fallback доступны повторное чтение и выгрузка исходных строк в web. Автоматическое «исправление» путём очистки не выполняется.

### Покупки, настройки и онбординг

- Весь список покупок проверяется **до** существующей миграции. Некорректная запись блокирует загрузку всего списка; остальные продукты не записываются поверх исходного списка после фильтрации.
- Старые строки и записи с `text` поддержаны. Проверяются поля, результат миграции, количество записей и уникальность ID; порядок, checkbox и дополнительные поля сохраняются.
- Ошибка чтения/проверки настроек не сохраняет defaults. Существующая миграция отменённого `textSize` выполняется только для валидных настроек.
- Онбординг отличает `pending`, `completed`, отсутствующий ключ и неизвестный статус. При известном статусе ошибки чтения legacy-ключей не меняют прогресс. Первый маркер сохраняется до монтажа остальных провайдеров, чтобы новый пустой профиль не принимался за старую установку.

### Сохранение и конкуренция

- Отказ основной записи показывает ошибку. Предыдущее сохранённое состояние и поля формы остаются доступны; toast об успешном сохранении не показывается.
- Retry записывает уже рассчитанный результат, а не повторяет операцию сложения количества/добавления приготовления. После успеха вызывается исходное завершение действия: очистка поля или возврат с формы.
- Отказ обновления legacy-зеркала обозначается отдельно: основная книга уже сохранена, повтор касается совместимой копии.
- Операции одного ключа сериализованы; вычисление результата импорта выполняется внутри очереди над последним состоянием, а не над устаревшим React closure.
- Перед записью сравнивается прочитанная строка. Для первоначальной миграции и восстановления дополнительно проверяются источники. В браузерах с Web Locks используются межвкладочные блокировки для клиентов с этим кодом.
- При конфликте более новые данные не заменяются. Перед подтверждённым повторным чтением несохранённый рассчитанный результат архивируется; если архивировать его нельзя, чтение не сбрасывает pending-операцию.
- Экран ошибки не перемонтирует находящиеся под ним формы; скрытый фон исключён из accessibility tree. Длинное сообщение/кнопки можно прокрутить.

## Ключи, версии и recovery

Существующие ключи не переименованы и не очищаются:

```text
recipe-book-v1
recipes
recipe-meta-v1
shopping-list-v1
app-settings-v1
app-onboarding-v1
```

В текущие JSON не добавлен обязательный version/envelope: это не требуется для закрытия P0 и сохраняет совместимость с прежними читателями. При наличии `version`/`schemaVersion` поддерживается только `1`; неизвестные версии блокируют запись. Текущий безверсионный формат остаётся читаемым.

Дополнительные ключи `storage-recovery-v1:<исходный ключ>:<время>:<случайный суффикс>` хранят нетронутые исходные строки либо отложенный результат конфликтующей операции и её источники. Они не удаляются автоматически и не являются новой основной базой данных.

Web-кнопка «Сохранить исходные данные в файл» создаёт `recipes-recovery-*.json` (`format: recipes-storage-recovery`, `version: 1`). Это **диагностический recovery-файл**, не обычная переносимая копия рецептов и не файл для автоматического импорта. Он может содержать личные заметки: его не следует публиковать. У непрочитанного ключа явно отмечается `error`, а `raw: null` не означает, что ключ доказанно пустой. При ошибке записи файл также содержит рассчитанный pending-результат.

Обычный `recipes-backup` **v1** и его валидатор/merge не изменены. Его импорт, экспорт и повторное добавление проверяются существующими тестами. Полный профиль и нативный файловый адаптер остаются следующим этапом.

## Проверки

Команды:

```powershell
npm test
npm run typecheck
npm run lint
npx playwright test --grep-invert '@visual' --workers=3
```

Unit-тесты проверяют три destructive-сценария из аудита, независимость чтения, пустой профиль, неизвестные схемы, повторные миграции, архивирование и его отказ, retry без повторного сложения, параллельные операции, устаревшего писателя и отказ legacy-зеркала. Browser-тесты воспроизводят ошибки через `Storage.prototype`, используют вымышленные данные и сверяют исходные строки после Retry/reload. Дополнительно проверяются сохранение формы/заметки/оценки при отказе, настройки, импорт и recovery-download.

Итоговый прогон на окончательном коде:

- `npm test`: **46/46**, включая 20 новых проверок слоя хранения.
- `npm run typecheck`: exit 0.
- `npm run lint`: exit 0.
- Полная функциональная Playwright-suite: **132 случая**, итог `128 passed, 4 skipped`, exit 0. В 128 принятых результатов входит один существующий `test.fail` для trusted-touch long-press на mobile Chromium; это не 128 обычных успешных сценариев. Неожиданных падений нет.
- Профили: desktop Chromium, mobile Chromium и iPhone WebKit. Все 13 сценариев `storage-safety.spec.ts` проходят в каждом профиле (39 проверок), включая две вкладки, сохранение приготовления и recovery-download.
- Три destructive-сценария из аудита повторены отдельно в unit-тестах и в каждом из трёх браузерных профилей: исходные payload не уничтожаются. При валидной основной книге она остаётся доступна; при повреждении без fallback запись блокируется; невалидные покупки не мигрируют в `[]`.
- `git diff --check`: ошибок whitespace нет. Существующее предупреждение Node о `MODULE_TYPELESS_PACKAGE_JSON` не приводит к падению unit-тестов; module mode проекта ради его устранения не менялся.

Поэтапные первые прогоны выявили перемонтирование формы при показе ошибки и устаревшие ожидания retry; они исправлены и перепроверены. Тест приготовления первоначально не находил кнопку из-за иконки в accessible name; исправлен локатор, без изменения логики приготовления. Приведённые выше результаты относятся к финальному прогону после этих исправлений.

## Оставшиеся ограничения

1. Web Locks защищают только участвующие клиенты. Старые уже открытые версии не используют эту блокировку; AsyncStorage не предоставляет общий атомарный compare-and-set. Проверка строк обнаруживает устаревшее состояние, но не даёт полной транзакционной гарантии против старого клиента, пишущего между проверкой и записью. Нельзя объявлять такую гарантию без смены протокола/хранилища.
2. Неподтверждённая запись при отказе остаётся в памяти до retry или выгрузки recovery. Закрытие вкладки/приложения до этих действий может потерять именно несохранённое изменение, но не прежний commit.
3. Полностью повреждённый payload нельзя автоматически превратить в исправные рецепты без валидного источника. Исходник сохраняется для ручного разбора; неизвестная версия требует совместимого обновления. Отдельного UI импорта диагностического recovery-файла пока нет.
4. Recovery-архивы занимают место. При исчерпании квоты восстановление останавливается до замены исходника; автоматической очистки архивов или пользовательских данных нет.
5. Реальный установленный iPhone PWA, системное меню Share, обновление старой сборки поверх новой на одном origin и нативные сборки этим браузерным прогоном не проверены. Visual baselines не обновлялись. Известный trusted-touch long-press defect не является исправлением этого этапа.
