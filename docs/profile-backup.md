## Что входит в полную копию

- Все рецепты: ID, название, категория, время, полный список ингредиентов и шагов.
- Избранное и все записи приготовления с ID, датой/временем, оценкой и заметкой. Метаданные без соответствующего рецепта тоже сохраняются, а не отбрасываются молча.
- Покупки: ID, имя, текст, необязательное количество/единица, checkbox и **исходный порядок массива**. Временное представление «купленное вниз» не подменяет этот порядок при экспорте.
- Настройки: `theme`, `language`, `shoppingCompletedBehavior`.

Не переносятся незавершённый онбординг, поиск/фильтр текущего экрана, открытая форма, кеши и операционные журналы. После восстановления маркер онбординга устанавливается в `completed`. Дата предыдущей выгрузки — локальная служебная метка, а не пользовательская настройка нового устройства.

## Форматы файлов

### Рецепты: существующий `recipes-backup` v1

Формат и старые файлы сохранены. Кнопки «Выгрузить в файл» / «Загрузить из файла» по-прежнему предназначены для добавления рецептов, не замены покупок и настроек.

Ограничения v1 остаются прежними: 5 МиБ UTF-8, 5000 рецептов и до 5000 приготовлений на рецепт. Для большого профиля используется новый полный формат, а не обрезание данных до v1. Размер теперь измеряется общей функцией без зависимости от наличия `TextEncoder` в native runtime.

### Полный профиль: `recipes-profile-backup` v1

```json
{
  "format": "recipes-profile-backup",
  "version": 1,
  "exportedAt": "2026-10-21T12:00:00.000Z",
  "profile": {
    "recipes": [],
    "recipeMeta": {},
    "shoppingItems": [
      {
        "id": "item-1",
        "name": "Молоко",
        "text": "Молоко — 1 л",
        "quantity": 1,
        "unit": "л",
        "checked": false
      }
    ],
    "settings": {
      "theme": "system",
      "language": "ru",
      "shoppingCompletedBehavior": "moveDown"
    }
  }
}
```

`recipeMeta` использует текущую модель `{ recipeId: { favorite, cookings: [{ id, cookedAt, rating?, note? }] } }`. `quantity` и `unit` необязательны; отсутствие количества не заменяется нулём. Массив покупок сохраняет несовместимые единицы отдельными позициями.

Неизвестный format/version, некорректные поля/даты, повторяющиеся ID внутри одной области или неподдерживаемые настройки отклоняются целиком до записи. Полный файл обязан содержать все области; он не трактуется как набор частичных обновлений. Поддерживается UTF-8 BOM.

Для полного формата не перенесены произвольные ограничения v1 на число рецептов/приготовлений или 5 МиБ. После 5 МиБ показывается предупреждение, данные не сокращаются. Практические ограничения памяти, времени JSON-разбора, FileSystem и квоты AsyncStorage сохраняются: огромный файл может быть непосилен конкретному устройству. Streaming/chunked backup в этом этапе не реализован.

## Две разные операции

### Добавить рецепты

Принимает старый v1 и новый полный файл. Из полного берутся только рецепты/избранное/история; покупки и настройки не импортируются. Preview показывает новые рецепты, дубликаты и конфликты. При конфликте ID и различном содержимом оба рецепта сохраняются, метаданные привязываются к новому ID.

История объединяется по идентичности события, а не только по одинаковой заметке. Повтор того же ID с тем же временем/оценкой/заметкой пропускается. При конфликте содержимого ID дополняется `-import-N`. Числовой суффикс зарезервирован существующим импортом; при повторе такой записи учитываются исходный ID и содержимое. Произвольный суффикс вроде `-import-handwritten` не считается этим служебным ID. Разные независимые ID с одинаковым содержимым сохраняются. Это явное правило совместимости с прежними импортами, не семантическое определение того, было ли приготовление «тем же самым».

После объединения приготовления сортируются по `cookedAt` от новых к старым, при равенстве — по ID. Поэтому существующие вычисления последнего приготовления/оценки/заметки работают с правильным порядком. Повтор файла не создаёт новые события или рецепты.

### Восстановить профиль

Принимает **только** полный формат. Preview показывает количество рецептов/любимых/приготовлений/покупок и галочек, примеры названий, настройки и число текущих записей. Кнопка явно подтверждает **замену всех областей**, а не добавление продуктов.

Покупки восстанавливаются как снимок со стабильными ID и порядком. Нормализатор добавления ингредиентов и суммирование количеств здесь не вызываются. Повторное восстановление того же файла даёт тот же профиль, а не удвоенные количества.

Отмена выбора, отмена preview и ошибка валидации не меняют пользовательские ключи. Если профиль изменился после preview, подтверждение отклоняется; нужно выбрать файл заново и проверить актуальное состояние.

## Безопасная запись нескольких областей

Внутренний формат шести существующих ключей не поменялся. Новые служебные ключи:

- `profile-restore-v1`: журнал операции с ID, статусом и точными строками `before`/`after` для фиксированного перечня ключей.
- `storage-recovery-v1:profile:<id>`: прежний журнал перед следующей операцией; предыдущие исходники не выбрасываются при повторном восстановлении.
- `profile-backup-last-success-v1`: локальная дата последней передачи полного файла для сохранения.

Протокол:

1. Дождаться текущих операций Context-провайдеров и захватить согласованный снимок для preview/экспорта.
2. При подтверждении взять общую блокировку профиля и сравнить исходные строки с preview.
3. Сохранить и прочитать обратно журнал `prepared` **до первой записи пользовательских ключей**.
4. Последовательно записать и проверить области и совместимые legacy-зеркала. Ещё раз сверить весь результат, затем записать и проверить `committed`.
5. Только после commit перечитать Context-провайдеры и сообщить об успехе.
6. При отказе перейти в `rollingBack`, восстановить точные строки `before`, проверить их и записать `rolledBack`. Если ключа до операции не было, удаляется только созданное этой операцией значение этого конкретного ключа; существующие пользовательские записи не очищаются.

Если откат тоже прерван, приложение показывает блокирующее сообщение. При следующем запуске `ProfileStorageGate` читает журнал **до** онбординга и провайдеров, завершает откат и только затем разрешает работу. Обычные записи Этапа 1 также проверяют маркер, чтобы другая вкладка не начала автосохранение в частично восстановленное состояние.

`committed`/`rolledBack` не переигрываются на следующем запуске: нельзя затереть изменения, которые пользователь сделал после восстановления. Исходный журнал остаётся сохранён. Если внешний старый клиент записал строку, не равную ни `before`, ни `after`, автоматический откат блокируется: третье значение не перезаписывается. Доступна выгрузка диагностического recovery с журналом и прочитанными текущими строками. Неизвестный или повреждённый журнал тоже блокирует запись, не удаляется и не подменяется пустым.

Web Locks координируют новые участвующие вкладки; в одном native runtime используется очередь. Старые открытые версии приложения не знают этого протокола. AsyncStorage не даёт общей транзакции/CAS против таких клиентов: перед переносом следует закрыть остальные вкладки/старые экземпляры. Полной гарантии для неучаствующего писателя между последней проверкой и записью не заявляем.

Журнал хранит исходник и целевой снимок дополнительно к текущим данным и legacy-зеркалам. Нужен запас свободного места. При невозможности подготовить журнал live-данные не меняются; при последующем отказе используется откат. Старые recovery-архивы не очищаются автоматически. Кнопки восстановления предыдущего **успешно** заменённого профиля в настройках пока нет: журнал остаётся техническим источником для восстановления, а не новым пользовательским списком копий.

## Файловые адаптеры

Web оставлен отдельным `.web.tsx`: `<input type=file>`, `File`, download URL либо Web Share при поддержке. Общая форма preview/confirm и логика формата одинаковы с native.

Native использует [DocumentPicker SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/document-picker/) с `copyToCacheDirectory: true`, [FileSystem SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/filesystem/) (`File`, `Paths.cache`, `text()`, `write()`) и [Sharing SDK 57](https://docs.expo.dev/versions/v57.0.0/sdk/sharing/) (`isAvailableAsync`, `shareAsync`). Не используются устаревшие FileSystem-функции из корневого модуля. Выбор отменён — нет импорта; ошибки чтения/недоступность Share показываются, не затрагивая данные.

«Последняя выгрузка» означает передачу файла браузеру/системному Share, а не доказательство записи на диск или облачной синхронизации. Web Share cancellation не обновляет дату. Native `shareAsync` не сообщает, сохранил ли получатель файл, поэтому фактическое наличие и пригодность файла нужно проверить вручную. При ошибке записи самой даты UI сообщает отдельно: уже выданный файл от этого не становится невалидным.

JSON не зашифрован, содержит личные заметки. Не публикуйте файл. Не удаляйте старую PWA/её данные, пока не проверили импорт на новом устройстве.
