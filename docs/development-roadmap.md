# План развития приложения в MonoRec

Основание: аудит от 21 октября 2026 года (локальный отчёт, не хранится в репозитории). Это план будущих изменений, а не описание выполненной реализации. Сейчас разрешены только аудит и документация; перечисленные команды изменения/сборки/выпуска в этом аудите не запускались.

## 1. Порядок и ограничения

Последовательность: **защита хранения → полный перенос → стабилизация проверок и зависимостей → брендинг/иконки/дизайн → настройки/About → native preview → контролируемый выпуск**. Отдельные нативные адаптеры переноса можно готовить параллельно после фиксации файлового контракта, не затрагивая работающую web-реализацию.

Сохранить:

- production origin `https://neyroshi-recipes.expo.app`, manifest URL, `start_url: /`, `scope: /`;
- EAS `owner`, `projectId`, текущий update URL; GitHub-репозиторий можно оставить с именем `recipes`;
- старые storage keys и читаемость JSON `format: recipes-backup`, `version: 1`;
- ID рецептов/приготовлений, количество товаров, отметки и пользовательский порядок;
- текущие поиск, фильтры, Smart Random, жесты, Safe Area, управление высотой web-root, темы и RU/EN.

Не совмещать смену хранилища, домена, схемы данных и полный визуальный редизайн в одном выпуске. Не заставлять пользователя удалять PWA ради новой иконки или названия. Откат JS не должен требовать отката пользовательских данных.

## 2. Этап 0 — зафиксировать исходное состояние

Приоритет: P0. Уже есть рабочий commit `8277354` и незакоммиченные доработки иконок/выравнивания. Сначала отдельно просмотреть и зафиксировать их, не смешивая с миграциями.

Действия после разрешения на реализацию:

1. Создать небольшие независимые изменения для хранения, переноса, брендинга и native-конфигурации.
2. Сохранить release-идентификатор, URL и список поддерживаемых схем. В дальнейших тестах использовать вымышленные данные, а не файлы реальных пользователей.
3. Зафиксировать старую и новую версии для теста обновления на одном origin. Проверка reload/new tab существующими E2E полезна, но не равна обновлению приложения.

Готовность: есть воспроизводимая исходная web-сборка, список существующих ключей и фиксированные тестовые данные с рецептами, любимым, несколькими приготовлениями, покупками разных единиц, галочками и обоими языками.

## 3. Этап 1 — исключить потерю данных при загрузке и записи

Реализовано и проверено локально 21 октября: защита чтения/commit/retry и явное recovery добавлены без смены существующего формата. 46 unit-тестов проходят; функциональная browser-suite: 132 случая, 128 принятых результатов (включая один известный expected failure) и 4 пропуска. Три destructive-сценария больше не уничтожают исходные данные. Результаты и границы гарантий — в [storage-safety.md](storage-safety.md). Этот отчёт не является разрешением на публикацию или началом следующих этапов; real-device проверка и обновление старой установленной PWA остаются отдельными действиями.

Приоритет: **P0, блокирует объявление безопасного обновления**.

Основные места: `src/context/recipes-context.tsx`, `shopping-context.tsx`, `settings-context.tsx`, `onboarding-context.tsx`; небольшой общий модуль хранения/миграций вне `src/app`, если это уменьшит дублирование.

### Изменения

- Явные состояния загрузки: `loading`, `ready`, `error`, `unsupported`. Отсутствующий ключ — отдельный нормальный случай; ошибка чтения, неверный JSON и неизвестная схема — не пустая книга.
- Не запускать автосохранение значений по умолчанию после неуспешного чтения. Сбой чтения зеркала не должен скрывать исправный основной снимок: читать/проверять основной снимок независимо.
- При повреждении сохранить исходный payload и дать повторить чтение/получить recovery-файл. Миграция выполняется после успешной валидации, с проверкой результата. При ошибке записи исходные данные остаются доступными.
- Не превращать неподдерживаемые записи покупок в молча отфильтрованный список. Зафиксировать правила частичного восстановления и показать пользователю результат.
- Добавить версионирование внутренних снимков с чтением текущего безверсионного формата. Будущую неизвестную версию открывать без перезаписи либо блокировать с объяснением.
- Отображать отказ записи и возможность повторения. Toast «Сохранено» связывать с успешным сохранением. Обозначать несохранённые изменения, если UI остаётся оптимистичным.
- Сериализовать связанные операции и определить защиту от устаревших данных при импорте/нескольких вкладках. Проверка ревизии должна учитывать асинхронную гонку; простая очередь одного React-провайдера не даёт межвкладочной гарантии.
- Не вводить полную транзакционную базу без необходимости. Основной снимок книги уже существует. Для остальных данных выбрать минимальный безопасный commit-протокол, не считать `multiSet` общей атомарной транзакцией.

### Обязательные проверки

| Сценарий | Ожидаемый результат |
| --- | --- |
| Новый пустой профиль | Чистая книга и корректный онбординг |
| Валидный основной снимок, ошибка чтения legacy-ключа | Книга сохранена; исходный снимок не заменён пустым |
| Повреждённый основной снимок, валидные зеркала | Контролируемое восстановление без потери доступных записей |
| Нет ни одного пригодного источника | Ошибка/recovery, исходные строки не переписаны |
| Ошибка/неизвестный формат покупок и настроек | Никакой автоматической замены пустыми/дефолтными значениями |
| Отказ или квота при сохранении | Нет ложного успеха, можно повторить, старые данные доступны |
| Повтор миграции и перезапуск в середине | Те же ID, история, количества, галочки и порядок |
| Старая версия видит будущую схему | Не перезаписывает её старым форматом |
| Изменения из двух вкладок или во время импорта | Нет молчаливой потери новых изменений |

Готовность: три воспроизведённых в аудите destructive-сценария больше не уничтожают исходные payload; штатные сценарии текущего приложения проходят без очистки ключей.

## 4. Этап 2 — полноценная резервная копия и перенос

Статус 21 октября: web-часть, отдельный полный формат, preview/confirm, исправление порядка истории, журнал rollback/recovery и нативный адаптер реализованы. 67 unit-тестов проходят; функциональная browser-suite: 159 случаев, 155 принятых результатов (один известный expected failure) и 4 пропуска. DNS-блокер снят npm-прокси: три Expo-модуля установлены, lockfile обновлён, TypeScript, ESLint и локальный JS-экспорт iOS/Android проходят. **Real-device перенос ещё не проверен**, бинарные production-сборки не выполнялись. По отдельному запросу опубликована PWA: выпуск `2brlxu34ys` на прежнем origin, preview smoke и проверка production-файлов пройдены. `npm audit` выявил 23 предупреждения, включая одно critical; безопасный разбор зависимостей остаётся в Этапе 3, автоматический `audit fix` не применялся. Контракт, проверки и файлы — в [profile-backup.md](profile-backup.md).

Приоритет: P1, обязателен перед приглашением существующих пользователей в native или на другой origin.

Web-экспорт/импорт рецептов не создавать заново. Расширить контракт `src/utils/recipe-backup.ts` и текущий web UI; общую логику оставить независимой от файловых API платформ.

### Контракт и поведение

1. Продолжать принимать `recipes-backup` v1. Для полного архива ввести явно версионированный формат, включающий рецепты, метаданные, покупки с ID/количествами/галочками/порядком и настройки. Статус онбординга — не пользовательская ценность: импорт должен выводить в приложение, а не переносить незавершённый тур.
2. Отделить добавление рецептов от восстановления полного профиля. Перед применением показывать состав файла и выбранные области. Восстановление с заменой, если вообще потребуется, должно быть отдельным явным действием с резервированием текущего состояния.
3. Для повторного импорта покупок использовать стабильные ID и правила конфликтов. Не применять автоматическое суммирование количеств, предназначенное для добавления ингредиентов.
4. Нормализовать порядок истории по дате при объединении и корректно вычислять последнее приготовление/оценку/заметку. Не терять отдельные события с одинаковым содержанием без зафиксированного правила идентичности.
5. Обеспечить восстановление при частично выполненной записи нескольких областей: предпочтительно один commit-снимок либо staging с маркером commit и идемпотентным восстановлением. Сохранять исходный снимок до подтверждения результата. Не запускать массовую миграцию ради переименования.
6. Согласовать ресурсные лимиты экспорта и импорта: валидная книга, которую разрешено создать, должна оставаться выгружаемой. Учесть размер в UTF-8, длительную историю и дублирование web-хранилища зеркалами. Проверять предупреждения до исчерпания ресурсов, не ограничиваться общей ошибкой «Не удалось выгрузить».
7. Добавить видимую дату последней успешной копии и инструкцию переноса. Не заявлять автоматическую синхронизацию или шифрование: их нет. Контрольная сумма, если добавлена, проверяет целостность, но не является защитой от подмены или шифрованием.

### Нативный адаптер

Заменить `RecipeTransfer`-заглушку платформенным компонентом, который использует тот же валидатор/merge и preview. Рассмотреть SDK-совместимые [Expo DocumentPicker](https://docs.expo.dev/versions/v57.0.0/sdk/document-picker/), FileSystem и [Sharing](https://docs.expo.dev/versions/v57.0.0/sdk/sharing/). Уточнить FileSystem API по документации установленного SDK перед реализацией; не переносить устаревшие API из памяти.

При выборе файла обеспечить доступность прочитанного содержимого, обработку отмены, неподдерживаемого формата, отказа провайдера файлов и отсутствия приложения-получателя. Web-реализацию с `<input type=file>` сохранить отдельно.

Команда для будущего добавления выбранных модулей через Expo, не выполненная в этом аудите:

```powershell
npx expo install expo-document-picker expo-file-system expo-sharing
```

Проверить прямые зависимости, даже если FileSystem уже присутствует транзитивно. Не добавлять сервер или облачную базу ради ручного переноса.

### Готовность

- Файлы v1 продолжают читаться, повторный импорт не дублирует рецепты/историю/количества покупок.
- Копия полного профиля восстанавливается в чистой установке с теми же значимыми данными.
- Пройден путь PWA iPhone → Файлы → native iOS, а также PWA → Android и обратный экспорт; отдельные проверки на настоящих устройствах.
- Нет изменений исходного профиля при отмене, ошибке или неподдерживаемой версии файла.

## 6. Этап 4 — MonoRec, иконки и дизайн-система

Приоритет: P2, после защиты хранения.

### Переименование

- Изменить только display name в `app.json`, брендовый `appTitle` RU/EN, manifest `name`/`short_name`, apple-mobile-web-app-title, заголовок экспортированного HTML, README и брендовые тексты About/onboarding.

Уже подготовленные `cookbook-dark/light` и генератор использовать как исходник, не рисовать новые варианты без задания.

- Изменение native icon/splash выпускать новой бинарной сборкой, не только EAS Update.

### Дизайн-система

- Согласовать палитру и роли MonoRec поверх существующих `AppColors`/`THEMES`.
- Зафиксировать шкалу текста, отступов, радиусов и размеры интерактивных областей. Не добавлять самостоятельный регулятор размера текста.
- Поэтапно унифицировать кнопки, поля, заголовки секций, карточки и состояния загрузки/ошибки. В первую очередь убрать обход тем/локализации в новых error UI и swipe actions.
- Проверить обе темы, RU/EN, системный крупный текст, перенос длинного названия продукта, checkbox, свайп, drag, клавиатуру и нижнюю панель.
- Не менять проверенный `visualViewport`/Safe Area механизм в рамках смены названия.

Готовность: MonoRec одинаково назван в новых пользовательских поверхностях, новая графика согласована, старый профиль продолжает открываться по старой ссылке и экспортироваться.

## 8. Этап 6 — нативные preview-сборки EAS

Приоритет: P1 для native-переноса и конфигурации, P2 для распространения после закрытия данных.

### Решения перед первой сборкой

1. Выбрать постоянные `ios.bundleIdentifier` и `android.package` под контролем владельца. Пример `com.<owner>.monorec` — только схема именования, не утверждённые идентификаторы. Если уже есть реально распространявшаяся native-установка, сначала установить её ID и ключ подписи.
2. Сохранить существующий EAS project ID. Добавить `eas.json` с development, preview и production. Для development client добавить `expo-dev-client` через Expo; preview должен работать без Metro.
3. Задать build numbers/автоинкремент и каналы preview/production. Существующий `runtimeVersion: appVersion` требует повышения версии при изменении native runtime. Выбор `fingerprint` — возможное отдельное решение, а не необходимый шаг ребрендинга.
4. Не создавать `ios/`/`android/` вручную. Настраивать через app config и плагины, оставив CNG.
5. Проверить нативный импорт/экспорт, тему, splash, иконки, TypeScript runtime API на Hermes, gesture integration и настройки Android-клавиатуры. Web-only код должен остаться в `.web.tsx`/за platform guard.

Профили и параметры сверять с [EAS eas.json](https://docs.expo.dev/build/eas-json/) и [runtime compatibility](https://docs.expo.dev/eas-update/runtime-versions/). На этапе аудита `eas.json` не создан, build/configure/update/submit не запускались.

### Маршрут проверки

- Android: preview APK с embedded JS; установка на устройство, работа без компьютера, повторный запуск, импорт файла, обновление поверх предыдущего APK с тем же package/signing key.
- iOS: development/preview на зарегистрированном устройстве или TestFlight согласно выбранному способу подписи. Для EAS ad hoc нужен действующий доступ Apple Developer и UDID; simulator — отдельный профиль и проверка, не замена физическому iPhone.
- Native update: после нового build сохраняются ID приложения и подпись; данные сохраняются при штатной установке поверх старой. Удаление приложения и установка нового не являются тестом безопасного обновления.
- Проверить создание/редактирование/удаление рецепта, приготовление с оценкой/заметкой, избранное, поиск/фильтры/Smart Random, выбор ингредиентов, нормализацию покупок, отмену/сохранение свайп-редактирования, delete, checkbox, long press, длинный список, Android Back, клавиатуру и Home Indicator.

Будущие команды после настройки профилей и подписей:

```powershell
npx eas-cli@latest build --platform android --profile preview
npx eas-cli@latest build --platform ios --profile preview
```

Это не команды для выполнения сейчас. Проверить доступы владельца к Expo/Apple/Google; не собирать credentials в исходниках. Google Play-аккаунт нужен на этапе публикации в магазин, а не для ручного тестирования APK. Нативные файлы пользователя из PWA приходят только через явный импорт, не через общность названия MonoRec.

Готовность: два установленных preview-билда проверены на устройствах, путь файлового переноса и обновления поверх предыдущей установки подтверждён. Только после этого — отдельное решение о production build/TestFlight/store submission.

## 9. Этап 7 — контролируемый выпуск PWA и native

Приоритет: завершающий этап, выполняется только по отдельному запросу на публикацию.

1. Проверить чистоту релизного коммита, версии и все обязательные проверки. Сохранить предыдущий deploy и план отката кода.
2. До изменения origin или формата обеспечить доступную пользователю копию. На существующем origin без изменения схемы не запускать ненужную миграцию.
3. Для PWA собрать web export, сначала проверить preview с тестовыми данными. Preview имеет другой origin: данные от production там не появятся автоматически.
4. Проверить обновление на том же origin в отдельном тестовом окружении, затем проверить совместимость production-выпуска без очистки storage. Исходные данные должны оставаться читаемыми при повторном запуске/ошибке миграции.
5. После разрешённого production deploy сравнить опубликованный JS с локальной сборкой, проверить HTML title, manifest и обе иконки. Новые имена не должны создавать второй EAS-проект или скрывать старое хранилище.
6. Для native разнести EAS Hosting, EAS Build и EAS Update: web deploy не обновляет уже установленный бинарный файл; update не меняет native icon/modules. Store submission — отдельное действие.
7. После выхода собрать feedback с номером выпуска. Ошибку миграции решать восстановлением/retry, не советом очистить данные.
