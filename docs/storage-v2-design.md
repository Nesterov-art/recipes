# Этап 7.2: безопасное хранение профиля на iOS и Android

Дата: 27 октября 2026 года. Статус: **реализовано локально, не закоммичено**. Утверждено направление A + B + C + D и, условно, G. Web/PWA работает на прежней схеме без изменений. Самостоятельной сборки ещё нет, поэтому всё, что касается устройства, — «не проверено».

## 1. Почему понадобилось

Модель из [native-builds.md](native-builds.md) показала два предела Android AsyncStorage:
- одна строка SQLite читается через буфер (CursorWindow) около 2 МиБ;
- вся база ограничена 6 МиБ.

Прежний журнал восстановления хранил полные строки «до» и «после», а книга — ещё и в двух зеркалах. Поэтому:
- примерно при 250–290 рецептах журнал переставал читаться, и приложение блокировалось;
- примерно при 1000 рецептах не читалась уже сама книга.

Факты платформ, на которые опирается решение:

- **Android.** Одна запись (`setItem`) — одна транзакция SQLite. Несколько вызовов из JS **не** считаются одной транзакцией.
- **iOS.** Значение больше 1024 символов пишется в файл атомарно, затем атомарно перезаписывается `manifest.json`. Несколько ключей не атомарны.
- **expo-file-system.** `move` с перезаписью сначала удаляет файл назначения, поэтому файловый вариант не выбран.

## 2. Схема хранения

**Web** — без изменений: `src/utils/app-storage.ts` использует прежний AsyncStorage (localStorage) с зеркалами и журналом v1.

**iOS и Android** — `src/utils/app-storage.native.ts`. Логические ключи прежние (`recipe-book-v1`, `shopping-list-v1`, `app-settings-v1`, `app-onboarding-v1` и другие), а физически каждое значение хранится так:

```text
mr2:<ключ>                 манифест: {"format":"monorec-value","version":2,"current":<поколение>|null,"prev":<поколение>|null}
mr2:<ключ>#<id>.<n>        часть n поколения id, не больше 256 КиБ UTF-8
поколение = { id, length, sum, inline? | parts: [{ length, sum }] }   до 32 КиБ — прямо в манифесте
```

- **Целостность.** У каждой части и у значения целиком есть длина и контрольная сумма (cyrb53). Несовпадение — ошибка `read`. Пустое или частичное значение никогда не возвращается.
- **Поколения.** Хранятся текущее (`current`) и одно предыдущее подтверждённое (`prev`). Более старые удаляются после фиксации.
- **Зеркала.** На native книга пишется без зеркал `recipes` и `recipe-meta-v1`. Старых нативных клиентов нет.
- **Журнал восстановления v2.** Ключ `profile-restore-v2` хранит только манифесты «до» и «после» для четырёх ключей — несколько КиБ, без копий данных. Новых `storage-recovery-v1:profile:*` не создаётся.
- **Очередь.** Записи одного ключа идут последовательно. Операции профиля проходят через общую блокировку `withProfileLock`. Перед заменой манифеста проверяется, что он не изменился с момента подготовки.

### Точка фиксации и аварийное завершение (одно значение)

| Шаг | Если процесс завершится здесь |
| --- | --- |
| 1. Чтение текущего манифеста | Ничего не изменено |
| 2. Запись частей нового поколения (новые ключи) | Манифест указывает на прежнее поколение. Новые части — «сироты», их уберёт сборка мусора при запуске |
| 3. Проверочное чтение всех частей | То же |
| 4. **Запись манифеста — точка фиксации** (одна атомарная запись) | До неё — прежнее значение, после — новое. Смеси нет |
| 5. Удаление поколений, на которые не ссылаются ни манифест (`current`, `prev`), ни незавершённый журнал | Остатки уберутся при следующем запуске |

Unit-тест «killed at any write» завершает процесс на каждой записи по очереди. После перезапуска значение всегда в точности старое или новое, «сирот» нет.

### Восстановление профиля (несколько ключей)

1. Проверить, что профиль не изменился после предпросмотра.
2. Оценить место: если `текущий объём + новый профиль + 64 КиБ > 0,9 × лимит базы`, восстановление отклоняется до первой записи (`space`).
3. Подготовить новые поколения всех четырёх ключей. Манифесты пока не трогаются.
4. Записать журнал `prepared` и прочитать его обратно. Он закрепляет поколения обеих сторон от удаления.
5. Переключить манифесты по одному.
6. Прочитать и проверить все значения, затем записать журнал `committed`.

При любой ошибке или после аварийного завершения на шагах 4–6 при следующем запуске выполняется откат:
- каждый манифест возвращается к записи «до»;
- если там окажется третье, неизвестное значение, откат останавливается с ошибкой `recovery` и ничего не перезаписывает.

Тест «restore killed at every write» проверяет каждую запись: после перезапуска профиль целиком прежний или целиком новый. Тест «a failure of any single write» проверяет то же для ошибки любой отдельной записи без завершения процесса.

## 3. Старые данные

**Чтение.** Если манифеста нет, читается прежний физический ключ. Это и есть путь миграции. Если на месте прежнего ключа стоит маркер `monorec-storage-v2`, а манифеста нет — это ошибка целостности, а не пустое значение.

**Миграция** (`migrateLegacy`, при запуске, после восстановления журналов):
1. Прочитать все прежние ключи. Если хоть один не читается или не проходит проверку моделей, миграция пропускается и ничего не записывается. Ошибку покажут сами хранилища.
2. По одному ключу записать значение в новую схему и прочитать обратно. Каждое промежуточное состояние содержит те же данные. Прерванная миграция завершается при следующем запуске.
3. Последним записать маркер в физический `app-onboarding-v1`. Старые сборки читают его как неподдерживаемое состояние онбординга и останавливаются до записи, вместо того чтобы молча работать со старыми данными.
4. Прежние значения книги, зеркал, покупок и настроек **не удаляются**.

**Старый журнал v1:**
- Читаемый и незавершённый — откатывается прежним кодом поверх нового слоя.
- Нечитаемый (больше 2 МиБ) — приложение блокируется с аварийной выгрузкой (раздел 5), без изменений данных.

**Откат версии приложения** не поддерживается. Старый код видит только прежние ключи, а после миграции — маркер.

## 4. Очистка

Удаляются **только** части вида `mr2:<ключ>#<id>.<n>`, на которые не ссылаются ни манифест (`current`, `prev`), ни незавершённый журнал v2. Если журнал не читается, части не удаляются вообще. Не трогаются:
- неизвестные ключи;
- части с нестандартным именем;
- прежние `storage-recovery-v1:*`.

**Очистка прежних данных** (`cleanupLegacy`) выполняется только явным вызовом. Автоматически она не запускается и к интерфейсу пока не подключена. Условия:
1. Миграция завершена (маркер и манифест онбординга).
2. Журналы v1 и v2 завершены.
3. Есть полная выгрузка профиля, **сделанная после миграции**.
4. Книга, покупки и настройки читаются из новой схемы и проходят проверку.

Тогда прежние значения заменяются коротким маркером. Это не удаление: старый код увидит неподдерживаемые данные, новый не примет маркер за данные. В тесте объём падает более чем вдвое.

## 5. Аварийная выгрузка

Выгрузка доступна на любом блокирующем экране хранилища, на native — через существующий `expo-sharing` ([storage-recovery-export.tsx](../src/components/storage-recovery-export.tsx), [emergency-export.ts](../src/utils/emergency-export.ts)). Она только читает: каждый ключ отдельно, ошибки запоминаются, ничего не исправляется и не перезаписывается.

- **Профиль целиком читается и проверен, журналы завершены** → «Сохранить полную копию профиля», обычный `recipes-profile-backup` v1.
- **Иначе, если читается книга** → «Сохранить книгу рецептов», обычный `recipes-backup` v1. Пользователь видит пояснение, что полная копия недоступна. Одно значение согласовано само по себе, даже если состояние журнала неизвестно.
- **Всегда** → «Сохранить диагностический файл» (`monorec-emergency-diagnostic`). В нём `complete`, список нечитаемых ключей и тексты ошибок. Если файл неполный, это видно в имени (`-incomplete`) и в тексте на экране. Файл явно помечен как не резервная копия.

Кнопки «Отложить восстановление» нет. Очистка данных приложения не предлагается.

## 6. Размер базы Android

Локальный config plugin [`plugins/with-async-storage-size.js`](../plugins/with-async-storage-size.js) задаёт `AsyncStorage_db_size_in_MB=32` в `android/gradle.properties`. Новых зависимостей нет: используется `expo/config-plugins`. `expo config --type introspect` подтверждает значение. `AsyncStorage_useNextStorage` не задаётся, по умолчанию `false`.

Это свойство читает `config.gradle` используемого (прежнего, SQLite) варианта библиотеки и передаёт в `setMaximumSize`. **Требует новой сборки. В Expo Go не действует**, поэтому там бюджет восстановления считается от 6 МиБ. Лимит одной строки от этого параметра не зависит: его обеспечивает разбиение на части.

## 7. Измерения (unit, синтетические данные, эмуляция Android)

Длинные рецепты: 8–14 ингредиентов, 6 длинных шагов на русском, 10 приготовлений с заметками на рецепт, 60 покупок. Каждый профиль восстановлен 6 раз подряд с чередованием двух профилей, затем выполнено обычное изменение книги.

| Рецептов | Файл профиля | Книга | Обычный объём (текущее + предыдущее) | Пик | Самое большое значение |
| --- | --- | --- | --- | --- | --- |
| 50 | 207 КиБ | 149 КиБ | 358 КиБ | 507 КиБ | 149 КиБ |
| 300 | 1,16 МиБ | 897 КиБ | 1,81 МиБ | 2,69 МиБ | 256 КиБ |
| 1000 | 3,85 МиБ | 2,92 МиБ | 5,91 МиБ | 8,83 МиБ | 256 КиБ |
| 2000 | 7,71 МиБ | 5,86 МиБ | 11,8 МиБ | 17,6 МиБ | 256 КиБ |

- Начиная со второго восстановления объём не растёт (отклонение меньше 64 КиБ).
- 1000 и 2000 рецептов **не помещаются в 6 МиБ** (Expo Go, сборка без плагина). Там восстановление честно отклоняется проверкой места.
- В пределах 32 МиБ пик для 2000 рецептов — 17,6 МиБ, плюс накладные расходы SQLite. Их нужно измерить на эмуляторе.

## 8. Осталось проверить в самостоятельной сборке

1. Калибровка предела строки на эмуляторе в отдельной тестовой сборке: значения 1,5 / 1,9 / 2,1 / 3 МиБ.
2. Фактическое применение 32 МиБ (заполнение тестового профиля), накладные расходы SQLite, сообщение о нехватке места.
3. Профили на 300, 1000 и 2000 рецептов: восстановление, перезапуск, изменение, повторное восстановление, принудительное завершение процесса во время восстановления.
4. Обновление `adb install -r` поверх предыдущей сборки: выгрузки до и после совпадают.
5. Аварийная выгрузка через меню «Поделиться» на Android и iPhone.
6. iPhone: профиль на 300 рецептов, восстановление, перезапуск, выгрузка. Скорость записи частей.

## 9. Следующие небольшие улучшения (не сделаны)

1. Читаемые имена файлов: уникальный каталог в cache вместо префикса `Date.now()-Math.random()`.
2. После меню «Поделиться» сообщать «Файл передан», а не «сохранён»; аварийная выгрузка уже так делает.
3. «Последняя выгрузка» — только для подтверждённого результата.
4. Удаление временных файлов в cache.
5. Фикстуры, выгруженные из production-PWA, для проверки импорта на native.
6. Ограничить число архивов конфликтов `SafeStore.archive`. Они редкие и создаются действием пользователя; на native уже хранятся частями.
7. Интерфейс для `cleanupLegacy` после подтверждённой выгрузки.
